# Выдача покупок по режимам

Плагин сверён с backend/src/game-servers.js, order-schema.js, order-store.js,
payments.js и data/products.json сайта. Backend, каталог, цены и production-данные
не изменяются. Плагин не создаёт и не мигрирует рабочие таблицы.

## Контракты

| orders.server | Внутренний server | Таблица в БД из JDBC | Резервирование |
| --- | --- | --- | --- |
| survival или classic | classic | orders_anarchy | Прежний путь |
| duels | duels | shop_orders, строго server=duels | Атомарный DB claim |
| minigames | minigames | shop_orders, строго server=minigames | Атомарный DB claim |
| hard (архив) | hard | orders | Прежний путь |

Для нового конфига нужен явный orders.server. Пустое/неизвестное значение отключает
**источник заказов**, сохраняя доступные источники Telegram и голосований.
В поставляемом конфиге server пустой специально, чтобы новый экземпляр не начал
обрабатывать чужой режим.

Имя БД задаётся mysql.jdbcUrl: обычный URL jdbc:mysql://host:port/database?параметры.
Поддерживаются имена БД из латинских букв, цифр и подчёркивания, длиной до 64 символов.
Старые table / orders.table разрешены только как проверка соответствия: строго
database.orders_anarchy, database.orders либо database.shop_orders. Другая БД,
неправильная таблица, произвольный SQL или конфликт с server отключают источник.
Таблицу нельзя использовать для перенаправления заказов между режимами.

Совместимость старого конфига действует только **без секции orders** и с явно
заданным table: database.orders_anarchy либо database.orders. Тогда используется
старый корневой tiers и выводится предупреждение о миграции. Неявного fallback на
Survival или Hard нет; shop_orders через этот путь запрещена.

## Примеры настройки

На каждом сервере установлен отдельный экземпляр плагина. В его конфиге указываются
один orders.server и один корневой tiers с командами именно этого сервера.
Общие mysql, polling и остальные секции берите из src/main/resources/config.yml.
Для каждого экземпляра задавайте собственный уникальный и стабильный workerId.

Survival SMP (classic также допустим в orders.server):

```yaml
orders:
  server: survival
  workerId: survival-1
  requiresOnline: false

tiers: {} # Оставьте здесь действующие команды Survival из старого tiers.
```

Duels:

```yaml
orders:
  server: duels
  workerId: duels-1
  requiresOnline: true

tiers: {} # Заполните настоящими командами Duels.
```

Команда валюты Duels не указана. Пустой tiers означает ожидание настройки
с диагностикой неизвестного tier.

MiniGames; команда подтверждена владельцем: /money give ник сумма.

```yaml
orders:
  server: minigames
  workerId: minigames-1
  requiresOnline: true

tiers:
  coins_10:
    - "money give ${nickname} ${grant_qty}"
  coins_50:
    - "money give ${nickname} ${grant_qty}"
  coins_100:
    - "money give ${nickname} ${grant_qty}"
  coins_500:
    - "money give ${nickname} ${grant_qty}"
  coins_1000:
    - "money give ${nickname} ${grant_qty}"
  coins_5000:
    - "money give ${nickname} ${grant_qty}"
```

Требование онлайна валютного плагина не подтверждено, поэтому для MiniGames
по умолчанию orders.requiresOnline: true. Плагин проверяет игрока до резервирования
и повторно перед каждой командой. Если после claim игрок вышел, резерв сохраняется
для сверки. orders.requiresOnline: false включайте после проверки поддержки
офлайн-выдачи конкретным обработчиком /money.

Архивный Hard можно оставить на старом конфиге с table: database.orders и корневым
tiers. Для нового формата задайте orders.server: hard и orders.workerId: hard-1;
свой существующий tiers оставьте на месте.

## Выдача и ограничения

- shop_orders: только paid, is_test=0, delivered_at IS NULL, свой server и NULL-токен.
  Выборка включает server, quantity, product_title, grant_qty и поля резерва,
  сортируется по paid_at, id и ограничена batchSize.
- В старых таблицах используется COALESCE(is_test, 0)=0. Новые колонки не запрашиваются.
- Каждый экземпляр использует один корневой tiers из своего конфигурационного файла.
  Его команды применяются только к заказам выбранного orders.server. На разных
  серверах одинаковые tier могут иметь разные команды. При смене режима проверьте
  также свой tiers; режим и команды фиксируются вместе при запуске исполнителя.
- Перед выдачей создаётся UUID попытки. UPDATE резервирует только свободную строку,
  увеличивает delivery_attempts и фиксирует worker. Команда разрешена только после
  affectedRows=1 и успешного commit. Во время Bukkit-команд транзакция не удерживается.
- Успех и ошибка проверяют id, order_id, server, токен, paid, is_test=0 и отсутствие
  delivered_at. Успех записывает delivered_at и delivery_note=ok, оставляя токен.
  Ошибка меняет только короткую безопасную delivery_note. Повторная попытка не
  начисляется при записи результата.
- SQL-повторы заново открывают транзакцию и повторяют только сохранение результата.
  Неоднозначный claim/commit не повторяется внутри попытки. Команды из SQL-retry
  никогда не вызываются.
- Неизвестный tier, ошибочный шаблон или офлайн до claim не резервируют shop_orders.
  После исправления mapping заказ доступен снова. Диагностика ограничена по частоте.
  Неразрешённые старые заказы в пределах batchSize требуют внимания: они могут
  занимать начало выборки и задерживать последующие покупки.
- Не очищаются даже старые токены. После остановки, таймаута, частичной команды,
  потери ответа БД или аварии возможна ручная сверка. Автоматического release нет.
- grant_qty берётся из заказа. quantity — число пакетов; дополнительного умножения,
  расчёта по tier/amount или обращения к текущим ценам нет.
  coins_1000, quantity=2, grant_qty=2200 -> одна команда money give Ник 2200.
  coins_5000, quantity=3, grant_qty=18000 -> одна команда money give Ник 18000.
- Прежние плейсхолдеры сохранены. Новые: ${server}, ${quantity}, ${product_title}.
  Для legacy server берётся из контракта, quantity=1 — техническое значение:
  историческое число пакетов в этих таблицах не хранится.
- Поддерживается Paper/Purpur 1.21.11, Java 21. Folia не добавляется.
  DB, чтение/создание конфигов и закрытие пула выполняются async.
  Размер каждого YAML-конфига ограничен 256 КиБ; разбор небольшого YAML выполняется sync.
  Онлайн-проверки и dispatchCommand выполняются sync через ограниченную очередь.
  После таймаута ещё не начавшаяся задача не выполнится позднее.
- /primerewards reload, /primerewards stats, алиасы и primerewards.reload сохранены.
  Reload сразу запрещает новые команды, асинхронно ждёт старые работы до 30 секунд,
  затем создаёт новые неизменяемые источники/исполнитель/пул.
  При превышении ожидания новые источники не запускаются; старые остаются остановленными.
  После завершения зависших работ повторите reload. Метрики нового диспетчера начинаются с нуля.
- При disable ожидание и закрытие БД вынесены async. При немедленном завершении JVM
  финальная запись может не успеть: сохранённый токен запрещает повторную выдачу.
- Настройки таймаутов ограничены. Не переопределяйте connectTimeout/socketTimeout
  в JDBC URL значением 0: параметры самого JDBC URL могут иметь приоритет над
  mysql.socket_timeout_ms.
- Голосования, Telegram и старые таблицы не получили распределённого claim:
  для каждого такого источника должен работать только один выдающий экземпляр.
  Их прежняя модель повторов сохраняется.

**Exactly-once для произвольных Bukkit-команд не гарантируется.** Возвращённый
dispatchCommand=true означает успешную передачу команды обработчику, а не
подтверждённую транзакцию валюты. Сам обработчик может отказать, отложить запись или
выполнить часть работы. Без идемпотентного API с ключом order_id невозможно атомарно
связать изменение игрового баланса с MySQL. Claim предотвращает конкурирующий
повтор через плагин и оставляет неопределённые результаты для проверки.

## Порядок обновления

1. Подготовьте резервные копии конфигов и БД штатными средствами. Остановите старые
   выдающие экземпляры; особенно те, которые могли читать shop_orders без server.
2. Убедитесь, что backend уже создал shop_orders с claim-колонками и InnoDB.
   Имя БД в JDBC должно совпадать с конфигурацией backend. Плагин схему не меняет.
3. Локально в IntelliJ соберите плагин: `.\gradlew.bat clean build`.
   Эта команда в рамках доработки не запускалась.
4. Проверьте сборку на dev-сервере и тестовой БД по разделу ниже.
5. На каждом игровом сервере задайте свой orders.server, уникальный workerId,
   JDBC и свой корневой tiers. Существующие команды Survival/Hard можно оставить
   на месте. Удалите конфликтующий корневой table.
   Существующие конфиги не перезаписываются и не дополняются автоматически.
6. Проверьте таблицы в tg_rewards.yml / votes_rewards.yml: они по-прежнему используют
   общий пул, но имеют собственные явно заданные имена таблиц. Не включайте одинаковую
   глобальную награду на нескольких серверах, если её старый источник этого не допускает.
7. Установите JAR и запустите серверы. В логах проверьте server, таблицу и workerId.
   Проверьте, что /money из консоли попадает в нужный валютный плагин и баланс меняется
   на grant_qty. Настройки рабочего плагина затем можно менять через /primerewards reload.

Не переносите и не дублируйте старые orders/orders_anarchy в shop_orders.

## Проверка локально

Сборки, тесты, подключение к MySQL и игровые команды при подготовке патча
**не выполнялись**. Выполнена статическая проверка diff.

Для реальной проверки SQL добавлена отдельная задача checkOrdersMysql. Обычные
build/test её не вызывают. Она не запускает Minecraft и не имитирует бизнес-успех
команды; проверяет настоящий InnoDB, SQL-условия и фиксируемое право одного победителя
продолжить после commit.

Создайте вручную НОВУЮ ПУСТУЮ локальную БД с именем, например, primerewards_test_local.
Тест принимает только localhost/127.0.0.1 и префикс primerewards_test_, отказывается
работать при наличии таблиц/представлений, не удаляет данные и оставляет свои фикстуры.
Используйте отдельную локальную MySQL-инстанцию/учётную запись.

В терминале IntelliJ установите PRIMEREWARDS_TEST_JDBC, PRIMEREWARDS_TEST_USER,
PRIMEREWARDS_TEST_PASSWORD, затем запустите вручную:

```powershell
$env:PRIMEREWARDS_TEST_JDBC = "jdbc:mysql://127.0.0.1:3306/primerewards_test_local?serverTimezone=UTC"
$env:PRIMEREWARDS_TEST_USER = "test_user"
# PRIMEREWARDS_TEST_PASSWORD задайте своим локальным способом без публикации пароля.
.\gradlew.bat checkOrdersMysql
```

Проверки охватывают алиасы и отказ от опасных конфигов, изоляцию таблиц/режимов,
paid/is_test/delivered/token, ORDER BY и LIMIT, две конкурирующие транзакции,
чужие токены/режимы, сохранение ошибок, повторный poll, неизменность чужих строк
и итоговые 2200/18000 из штатного mapping.

Дополнительно на dev Paper/Purpur:

| Сценарий | Ожидаемый результат |
| --- | --- |
| Три режима, одинаковые nickname/tier | Каждому выдаётся только его покупка |
| Два экземпляра одного режима | Одна команда, delivery_attempts=1 |
| Неизвестный tier | Нет команды/резерва; понятная запись в журнале |
| Игрок офлайн при requiresOnline=true | До claim строка не меняется |
| Игрок выходит после claim | Команда не начинается; резерв остаётся |
| Команда false/exception или частичная цепочка | Ошибка, токен сохранён, автоматического повтора нет |
| Зависший основной поток дольше command_timeout_ms | Просроченная очередь не выполняется после разблокировки |
| Потеря ответа commit перед командой | Без подтверждения команда не запускается; сверить резерв |
| Потеря БД после команды | Команда не повторяется при DB-retry/poll |
| Остановка/авария после claim | Токен сохраняется до ручной сверки |
| Reload меняет режим или JDBC во время работы | Старые команды запрещены, старые DB-результаты идут в старый источник |
| Повторный подписанный callback | Не снимает delivered_at/токен; выдача не повторяется |
| Старые таблицы без новых полей, Telegram, голосования | Прежние команды и формат хранения работают |

## Сверка зарезервированных заказов

1. Остановите **все** выдающие экземпляры соответствующего режима и дождитесь
   завершения их работ. Если /money инициирует асинхронную запись, дождитесь и её.
   Не снимайте резерв у ещё живого процесса.
2. В БД из JDBC найдите shop_orders с paid, is_test=0, delivered_at IS NULL и
   delivery_claim_token IS NOT NULL. Сверяйте id, order_id, server, delivery_worker,
   delivery_claimed_at, delivery_note, quantity и grant_qty. Токен используйте только
   в приватной административной процедуре; плагин не печатает его в лог.
3. По журналу валютного плагина/истории транзакций проверьте факт и сумму начисления.
   Один текущий баланс без истории обычно не доказывает результат.
4. Если полная выдача доказана, условно отметьте delivered_at и запись о ручной
   сверке, **оставив токен**. Обновление должно проверять id, order_id, server,
   точный прежний token, paid, is_test=0 и delivered_at IS NULL; ожидать одну строку.
5. Если доказано, что **ни одна команда не выполнялась**, администратор может
   контролируемо снять резерв с теми же условиями владения, очистив token/claimed_at/
   worker. Сохраните историю проверки и delivery_attempts; новая попытка увеличит
   счётчик при новом claim.
6. При частичной выдаче или недостаточных доказательствах оставьте резерв.
   Проведите индивидуальную сверку/докомпенсацию через реальный валютный инструмент.
   Не перезапускайте всю цепочку команд автоматически и не очищайте токены по возрасту.
