# Выдача покупок из shop_orders

Плагин сверён с backend/src/game-servers.js, order-schema.js, order-store.js,
payments.js и data/products.json сайта. Подготовлены код и примеры конфигов.
Backend, каталог, цены, production-данные и работающий Survival не изменяются.
Плагин не создаёт таблицы, не переносит историю и не переключает рабочую выдачу.

## Контракт и конфигурация

Все экземпляры читают **shop_orders в базе данных из mysql.jdbcUrl**. Для
jdbc:mysql://127.0.0.1:3306/external_data?... это external_data.shop_orders.

| orders.server | Фильтр server в shop_orders | Пример полного конфига |
| --- | --- | --- |
| survival | survival | [config-survival.yml](../examples/config-survival.yml) |
| duels | duels | [config-duels.yml](../examples/config-duels.yml) |
| minigames | minigames | [config-minigames.yml](../examples/config-minigames.yml) |

На каждом игровом сервере установлен отдельный экземпляр: один orders.server,
один уникальный стабильный orders.workerId и один корневой tiers с местными
командами. Перечислять другие серверы в его конфиге не нужно. Например:

~~~yaml
orders:
  server: survival
  workerId: survival-1
  requiresOnline: false
  query_timeout_seconds: 10

# Ниже остаётся весь действующий корневой tiers этого сервера.
~~~

Для Duels используются server: duels и workerId: duels-1, для MiniGames —
server: minigames и workerId: minigames-1. Команды tiers настраиваются отдельно.
Одинаковые nickname/tier в разных режимах не связывают заказы между собой.

orders.server обязателен. Отсутствующее, пустое, неизвестное значение и hard
отключают **источник заказов** с понятной диагностикой; доступные источники
Telegram и голосований продолжают работать. В поставляемом config.yml server
специально пустой. classic принимается только как алиас настройки и нормализуется
в survival; строки с server=classic не выбираются.

Имя БД берётся из обычного URL jdbc:mysql://host:port/database?параметры.
Допустимы латинские буквы, цифры и подчёркивание, длина имени до 64 символов.
Настройка table не нужна. Если сохранён table или orders.table со значением
orders_anarchy/orders, в том числе с именем БД, источник отказывается запускаться
и объясняет необходимость согласованного перехода после переноса истории.
Fallback и запросов к старым таблицам нет. Для совместимости допускается только
явное shop_orders либо <БД из JDBC>.shop_orders как проверка соответствия;
другая схема, таблица и произвольный SQL запрещены.

В полном примере Survival сохранены все команды из предоставленного старого
конфига, включая test и исторические товары. orders.requiresOnline: false
сохраняет прежнее поведение Survival; перед запуском проверьте, что его обработчики
команд поддерживают офлайн-выдачу. Сохраняйте mappings старых tier для уже созданных
и оплаченных заказов даже после удаления товара из products.json. Плагин не
пересобирает mapping по текущему каталогу.

В примере Duels tiers пустой: его реальные команды ещё не предоставлены.
Такие заказы остаются невыданными до заполнения mapping. В примере MiniGames
сохранена подтверждённая владельцем команда /money give ник сумма:

~~~yaml
tiers:
  coins_10:
    - "money give ${nickname} ${grant_qty}"
  coins_50:
    - "money give ${nickname} ${grant_qty}"
  coins_100:
    - "money give ${nickname} ${grant_qty}"
  coins_500:
    - "money give ${nickname} ${grant_qty}"
  coins_1000:
    - "money give ${nickname} ${grant_qty}"
  coins_5000:
    - "money give ${nickname} ${grant_qty}"
~~~

Для MiniGames и Duels requiresOnline: true — безопасное исходное значение.
Проверка выполняется до резервирования и перед каждой командой. Отключать её
можно после проверки офлайн-выдачи конкретного обработчика команды.

## Исторические заказы и количество

Миграцию Survival из orders_anarchy выполняют отдельно до согласованного
переключения. Она должна сохранить UUID order_id, исходные tier, amount,
grant_qty, статус, платежные данные и delivered_at. Канонический server — survival.
Плагин не меняет эти бизнес-поля. Существующий delivered_at исключает повторную
выдачу, даже если у исторического заказа нет claim-токена.

У перенесённых строк quantity и product_title могут быть NULL. Они передаются
как NULL, без подстановки 0, 1, tier или текущего названия товара. Если команда
использует только nickname/grant_qty, отсутствие этих метаданных выдаче не мешает.
Шаблон, который явно требует отсутствующий quantity/product_title, отклоняется
**до резервирования** с понятной ошибкой.

Сохранены прежние плейсхолдеры, доступны также ${server}, ${quantity},
${product_title}. Для валюты/ключей используется только готовый ${grant_qty}.
quantity — число пакетов, не дополнительный множитель. Нет вычисления по tier,
amount, текущему каталогу или ценам.

| Заказ MiniGames | Одна подготовленная команда |
| --- | --- |
| coins_1000, quantity=2, grant_qty=2200 | money give Ник 2200 |
| coins_5000, quantity=3, grant_qty=18000 | money give Ник 18000 |

## Резервирование и выполнение

- SELECT для всех трёх режимов требует status='paid', is_test=0,
  delivered_at IS NULL, server=? и delivery_claim_token IS NULL.
  Включены server, quantity, product_title, grant_qty и поля резерва.
  Сортировка paid_at, id; ограничение batchSize. Значения передаются параметрами.
- До claim проверяются режим, UUID, ник, наличие mapping, шаблоны и необходимый
  онлайн. Неизвестный tier или неправильный шаблон не резервируют заказ.
  Неразрешённые старые заказы в начале выборки могут задерживать следующие покупки;
  исправляйте mapping и следите за диагностикой.
- Для каждой попытки создаётся UUID токена. Короткий UPDATE проверяет id,
  order_id, server, paid, is_test=0, отсутствие delivered_at и токена; записывает
  token/claimed_at/worker и увеличивает delivery_attempts.
  Команды разрешены только при affectedRows=1 и подтверждённом commit.
  Во время Bukkit-команд транзакция не удерживается.
- Режим повторно проверяется перед командами. Источник, режим и mapping
  неизменяемы в рамках выполняющихся работ.
- Успех/ошибка проверяют id, order_id, server, точный токен, paid, is_test=0 и
  delivered_at IS NULL. Успех устанавливает delivered_at и delivery_note='ok'.
  Ошибка меняет только короткую безопасную delivery_note.
  Токен сохраняется в обоих случаях; счётчик попыток меняется только при claim.
- SQL-retry повторяет только запись результата, не команды. Неоднозначный claim
  или commit не даёт права запускать команды.
- После остановки, аварии, таймаута, частичной выдачи или потери ответа БД резерв
  остаётся для сверки. Нет автоматического снятия или перехвата старых токенов.
  Контролируемый release внутри плагина не реализован.
- Логи указывают режим, order_id и workerId; пароли и токены не выводятся.

**Exactly-once для произвольных Bukkit-команд не гарантируется.**
dispatchCommand=true означает передачу команды обработчику, а не подтверждение
транзакции валюты. Обработчик может отказать, отложить запись или выполнить часть
цепочки. Без идемпотентного игрового API с ключом order_id нельзя атомарно связать
игровое действие и MySQL. Claim защищает от конкурирующего повтора через плагин;
неопределённый результат требует проверки.

## Потоки и жизненный цикл

Сохраняется Paper/Purpur 1.21.11, Java 21; Folia не добавляется.
DB, файловое чтение/создание конфигов и закрытие пула выполняются async.
Небольшой YAML разбирается sync, размер каждого файла ограничен 256 КиБ.
Bukkit API, онлайн-проверки и dispatchCommand выполняются в основном потоке
через ограниченную очередь. Задача, просроченная до начала исполнения, не
выполнится позднее. Уже начатое действие стороннего плагина нельзя отменить.

Команды /primerewards reload, /primerewards stats, алиасы и права сохранены.
Reload сразу запрещает новые команды старого исполнителя, асинхронно ждёт его
работы до 30 секунд и затем заменяет источник, исполнитель и пул.
Если ожидание превышено, новые источники не запускаются, старые остановлены;
после завершения зависших работ требуется повторный reload.
Метрики нового диспетчера начинаются с нуля.

На disable ожидание и закрытие БД выполняются async. При немедленном завершении
JVM запись результата может не успеть, но сохранённый токен исключает повтор.
Не задавайте connectTimeout/socketTimeout=0 в JDBC URL: параметры URL могут
иметь приоритет над ограничениями пула.

Источники Telegram и голосований, их таблицы, команды и прежняя модель повторов
сохранены. Для каждого такого источника должен работать только один выдающий
экземпляр: распределённый claim к ним не добавлялся.

## Порядок обновления

Это план отдельного согласованного запуска. **Не заменяйте сейчас работающий
Survival и не удаляйте table из его старого конфига ради запуска нового JAR.**

1. Сначала локально соберите плагин в IntelliJ командой
   .\gradlew.bat clean build и проверьте его на dev-сервере с отдельной тестовой БД.
   В рамках этой доработки сборка и запуск не выполнялись.
2. Подготовьте отдельный новый конфиг каждого экземпляра по examples.
   Перенесите свои JDBC-реквизиты, весь действующий tiers и нужные настройки.
   Выберите server и уникальный стабильный workerId. В новых конфигах table
   отсутствует. Существующие файлы автоматически не перезаписываются.
   Проверьте также таблицы и включение tg_rewards.yml / votes_rewards.yml.
3. Согласуйте окно переключения и сделайте резервные копии БД/конфигов.
   Остановите старые выдающие экземпляры и дождитесь завершения работ.
   Согласуйте с backend обработку новых заказов и платежных callback на время
   переноса, чтобы они не писали в старое хранилище после финального переноса.
4. Отдельной административной процедурой перенесите историю Survival в
   shop_orders с сохранением order_id, платежных полей и delivered_at.
   Проверьте server=survival, исходные tier/grant_qty, созданные/оплаченные/
   выданные заказы, отсутствие дублирования UUID и допустимые NULL метаданные.
   Таблица должна соответствовать backend, иметь claim-поля и использовать InnoDB.
   Плагин этот шаг не выполняет.
5. Только после проверки миграции совместно включите новый backend и новые
   источники выдачи. JDBC должен указывать на ту же БД, что и backend.
   Проверьте режим/таблицу/workerId в журнале, историю магазина и выдачу на dev
   либо согласованных контрольных заказах.
6. Старый плагин после переключения не запускайте: оставшиеся записи старой
   таблицы могут отстать от новых выдач. Откат после начала работы требует сверки
   данных, а не простой замены JAR на старый.

## Проверка локально

Сборка, тесты, подключение к MySQL, миграция и игровые команды при подготовке
патча не выполнялись. Выполнена статическая проверка изменений.

Задача checkOrdersMysql запускается только явно; обычные build/test её не вызывают.
Она использует настоящий локальный MySQL/InnoDB, проверяет SQL и подготовку команд
без Minecraft. Счётчик победившей транзакции проверяет право продолжить после
commit, но не бизнес-успех Bukkit-команды.

Создайте вручную новую пустую локальную БД, например primerewards_test_local.
Проверка принимает только localhost/127.0.0.1 и префикс primerewards_test_,
отказывается работать при существующих таблицах/представлениях, не удаляет
данные и оставляет фикстуры. Создаётся только shop_orders, старых таблиц нет.
Используйте отдельную локальную MySQL-инстанцию/учётную запись.

В терминале IntelliJ задайте PRIMEREWARDS_TEST_JDBC, PRIMEREWARDS_TEST_USER и
PRIMEREWARDS_TEST_PASSWORD, затем вручную запустите:

~~~powershell
$env:PRIMEREWARDS_TEST_JDBC = "jdbc:mysql://127.0.0.1:3306/primerewards_test_local?serverTimezone=UTC"
$env:PRIMEREWARDS_TEST_USER = "test_user"
# Пароль задайте своим локальным способом без публикации.
.\gradlew.bat checkOrdersMysql
~~~

Проверки охватывают все три режима, classic, отказ от старого/неверного конфига,
paid/is_test/delivered/token, сортировку/LIMIT, конкуренцию двух транзакций для
каждого режима, чужие токены/заказы/режимы, повторные poll/claim/markDelivered,
сохранение резерва при ошибке и неизменность чужих строк/бизнес-полей.
Проверяются готовые команды 2200/18000, NULL метаданные, исторический оплаченный
tier и переход перенесённого created в paid с исходными UUID/tier/grant_qty.
Переход оплаты в фикстуре не проверяет подпись или сетевой callback backend.

Дополнительно на dev Paper/Purpur:

| Сценарий | Ожидаемый результат |
| --- | --- |
| Три режима, одинаковые nickname/tier | Каждый выдаёт только свой заказ |
| Два экземпляра одного режима | Только победитель claim запускает команды, attempts=1 |
| Неизвестный tier | Нет команды/резерва; понятная диагностика |
| Исторический оплаченный tier, NULL метаданные | Исходная команда с готовым grant_qty |
| Исторический delivered_at без токена | Нет повторной выдачи |
| requiresOnline=true, игрок офлайн до claim | Заказ не меняется |
| Игрок выходит после claim | Команда не начинается; резерв остаётся |
| Команда false/exception или частичная цепочка | Ошибка, резерв сохранён |
| Очередь просрочена до запуска | После разблокировки команды не начинаются |
| Потеря ответа commit перед командой | Команда не запускается; нужна сверка |
| Потеря БД после команды | DB-retry/poll не запускает команду повторно |
| Авария после claim | Резерв сохраняется до сверки |
| Reload меняет режим/JDBC | Старые команды запрещены, результаты идут в старый источник |
| Повторный подписанный callback | Не сбрасывает delivered_at/токен, нет повторной выдачи |
| Старые таблицы отсутствуют | Заказы работают только через shop_orders |
| Telegram и голосования | Прежние команды, права и формат хранения |

## Сверка зарезервированных заказов

1. Остановите все выдающие экземпляры соответствующего режима и дождитесь
   завершения их работ, включая отложенные операции сторонних обработчиков.
   Не снимайте резерв у ещё живого процесса.
2. Найдите в shop_orders строки с paid, is_test=0, delivered_at IS NULL и
   delivery_claim_token IS NOT NULL. Сверьте id, order_id, server, worker,
   claimed_at, note, tier и grant_qty. quantity/product_title могут быть NULL.
   Точный токен используйте только в приватной административной процедуре.
3. По журналам всех команд цепочки и истории транзакций установите фактический
   результат. Один текущий баланс без истории не доказывает начисление.
4. Если доказана полная выдача, отметьте delivered_at и результат ручной сверки,
   оставив токен. UPDATE должен проверять id, order_id, server, прежний токен,
   paid, is_test=0 и delivered_at IS NULL; ожидается ровно одна строка.
5. Только если доказано, что ни одна команда не выполнялась, допустимо
   контролируемо очистить token/claimed_at/worker с теми же проверками владения.
   Сохраните историю сверки и delivery_attempts; новый claim увеличит счётчик.
6. При частичной выдаче или недостатке доказательств оставьте резерв и выполните
   индивидуальную сверку/довыдачу через действующие игровые инструменты.
   Не повторяйте всю цепочку и не очищайте токены по возрасту.
